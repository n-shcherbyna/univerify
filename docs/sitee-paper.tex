\begin{abstract}
Fake academic diplomas are a growing problem worldwide,
yet checking whether a diploma is real still requires
slow, manual contact with the issuing university.
Blockchain registries can solve this by letting anyone
verify a credential on-chain---but on Ethereum, storing
data is expensive, so the way diplomas are represented
in a smart contract matters greatly.

This paper examines these costs using \emph{UniVerify},
a diploma-verification system built on Ethereum.
Two designs are compared: \emph{per-record storage},
where each diploma takes one contract slot, and
\emph{Merkle-batch issuance}, where a whole graduation
class is covered by a single cryptographic root.
To separate the effect of the architecture from
code-level choices, four Solidity contract variants
are tested with batch sizes from 1 to 4{,}096 diplomas.

The difference is substantial.
Merkle batching cuts the per-diploma issuance cost by
98.9\,\% for a class of 100 students and by three orders
of magnitude at 1{,}000 students---from \$4{,}820 down
to \$5.09 at current Ethereum prices.
Low-level EVM optimizations save another 6.6\,\% on
verification gas, but they are far less important than
the choice of architecture.
A closed-form model is also derived that decomposes the
optimization savings into a per-step and a constant term
and matches measured gas values with errors below 0.2\,\%.

The main conclusion is that for universities that issue
diplomas in batches, the data structure used on-chain
is the most important cost factor---not low-level code
tuning---and Merkle-batch registries are the practical
default for blockchain-based academic credentials.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The market for fake academic credentials is estimated
at over one billion dollars per
year~\cite{ezell2012degree}, but verifying whether a
diploma is genuine still depends on contacting the
issuing university---a process that is slow and hard to
scale across borders.
Blockchain-based registries offer a different approach:
once a diploma commitment is saved on-chain, anyone can
check it independently, without trusting a single
database.

The main obstacle is cost.
On Ethereum, every permanent storage write costs about
20{,}000~gas.
If each diploma is stored one by one, a university
issuing hundreds or thousands of diplomas per graduation
cycle faces very high fees.
The question is therefore not \emph{whether blockchain}
can be used for credentials, but \emph{how diplomas
should be stored on-chain so that costs stay reasonable}.

This paper addresses that question using
\emph{UniVerify}, a prototype diploma-verification
system.
Two approaches are compared:
\begin{enumerate}
  \item \textbf{Per-record storage} --- each diploma is
        saved in its own mapping slot and can be verified
        in constant time.
  \item \textbf{Merkle batch issuance} --- one Merkle
        root covers the whole graduation class; each
        diploma is verified with an off-chain proof.
\end{enumerate}

The main contribution is practical: this work measures the
gas cost of real, deployable Solidity contracts and
provides a closed-form model that predicts optimization
savings across different proof depths.

\subsection{UniVerify System}

UniVerify consists of a Solidity smart contract that
handles on-chain storage and verification, and an
off-chain TypeScript SDK that builds Merkle trees and
generates proofs.
Universities act as \emph{issuers} who publish diploma
commitments on-chain.
A verifier checks a diploma by providing the document
hash and, in the Merkle variant, a proof that the
diploma belongs to the published batch root.

\subsection{Contributions}

\begin{enumerate}
  \item A cost comparison of packed per-record storage
        and Merkle-batch issuance across deployment,
        issuance, verification, and revocation.
  \item A four-way benchmark of \Vpacked{}, \Vbase{},
        \Voz{}~\cite{openzeppelin}, and \Vopt{} that
        separates architectural, library, and EVM-level
        effects.
  \item A closed-form linear gas-savings model validated
        at six proof depths with errors below 0.2\%.
  \item An economic analysis that converts gas savings
        into real dollar costs for institutions.
\end{enumerate}

\section{Related Work}
\label{sec:related}

Grech and Camilleri~\cite{grech2017blockchain} identified
credential verification as one of the main uses of
blockchain in education.
Lizcano et~al.~\cite{lizcano2020decentralised} proposed
a decentralized credential system using IPFS and Ethereum
but did not analyze gas costs in detail.
Alketbi et~al.~\cite{alketbi2018blockchain} surveyed
blockchain applications in government services, including
education records.
The W3C Verifiable Credentials
standard~\cite{w3cvc2024} defines a data model for
tamper-proof claims but does not address cost.
Arndt et~al.~\cite{arndt2023onchain} measured on-chain
credential storage on Ethereum~L2 networks but did not
compare Merkle batching with per-record storage.

Merkle trees~\cite{merkle1987} are the standard way to
prove that an element belongs to a set.
OpenZeppelin's \texttt{MerkleProof}~\cite{openzeppelin}
is the most widely used Solidity library for this purpose.
Other approaches---sparse Merkle trees, Verkle
trees~\cite{verkle}, RSA accumulators---are not yet
practical for typical EVM contracts.

Ethereum execution costs are defined by the EVM gas
schedule~\cite{yellowpaper}, and EIP-2929 increased
costs for first-time storage access~\cite{eip2929}.
Most earlier work on blockchain credentials focuses on
architecture, privacy, or governance.
This paper takes a different approach: it measures how
specific Solidity design choices affect the gas cost
of issuing and verifying diplomas in an implemented contract.

\section{System Design and Methodology}
\label{sec:method}

\subsection{Two Verification Architectures}

Fig.~\ref{fig:arch} shows the two approaches.

\smallskip\noindent\textbf{Architecture~A --- Per-Record
Storage.}
Each diploma is stored in a
\texttt{mapping(bytes32\,$\Rightarrow$\,uint256)}.
The issuer address (160~bits) and a revocation flag
(1~bit) are packed into one 256-bit slot.
Issuing a diploma requires one \texttt{SSTORE};
verifying it requires one \texttt{SLOAD} plus bit
masking, which gives constant read cost.
This contract is intentionally kept simple and serves as
a cost baseline.

\smallskip\noindent\textbf{Architecture~B --- Merkle Batch.}
All diplomas in a graduation class form a Merkle tree
off-chain.
Only the 32-byte root is written on-chain through
\texttt{issueBatchRoot}, so one storage write covers the
whole batch.
To verify a diploma, the caller must provide
$d{=}\lceil \log_2 N \rceil$ sibling hashes.
Each leaf uses domain separation:
$\texttt{keccak256}(\mathit{contract}\|\mathit{chainId}
\|\mathit{issuer}\|\mathit{batchId}\|\mathit{docHash})$,
which prevents replay across contracts and chains.

\subsection{Optimization Techniques}
\label{sec:techniques}

The \Vopt{} variant targets two internal functions:
\texttt{\_processProof()} and \texttt{\_merkleLeaf()}.

\smallskip\noindent\textbf{T1 --- Unchecked loop.}
\texttt{unchecked\{++i;\}} removes the overflow check,
saving gas on each iteration.

\smallskip\noindent\textbf{T2 --- Scratch-space hashing.}
The two 32-byte inputs are placed directly in EVM
scratch memory and hashed in place, avoiding the cost
of \texttt{abi.encodePacked} memory allocation.

\smallskip\noindent\textbf{T3 --- Validation splitting.}
The public \texttt{merkleLeaf()} validates inputs;
a private \texttt{\_merkleLeaf()} skips those checks
and is used on internal paths.

\smallskip\noindent\textbf{T4 --- Assembly preimage.}
The 112-byte leaf preimage is packed using
\texttt{mstore}/\texttt{shl} instead of
\texttt{abi.encodePacked}.

\subsection{Experimental Setup}

All measurements were performed with Foundry~\cite{foundry2023}
(Solidity~0.8.20, optimizer set to 200~runs).
Merkle trees are built on-chain only in the test
harness; in a real deployment they would be built
off-chain.
Proof depths $d \in \{0,1,4,8,10,12\}$ correspond to
batch sizes from $2^0$ to $2^{12}$ (1--4{,}096 diplomas).
Gas values are function-level figures taken from
\texttt{forge test --gas-report}.

\subsection{Economic Interpretation}

Using a gas price of $g{=}40$~gwei and
$p{=}\$2{,}500$/ETH:
\begin{equation}
\mathrm{USD} = \mathrm{gas} \cdot g \cdot p \cdot 10^{-9}
\label{eq:usd}
\end{equation}

This gives \$4.82 per diploma for \Vpacked{} issuance
and \$5.09 for one Merkle batch root.
At graduation scale, the difference is striking:
100~diplomas cost \$482 with per-record storage versus
\$5.09 with batching; 1{,}000~diplomas cost \$4{,}820
versus \$5.09.
These numbers depend on network conditions:
at 10~gwei / \$1{,}500 (low activity) the 1{,}000-diploma
per-record cost drops to \$723, while at 80~gwei /
\$4{,}000 (high congestion) it rises to \$15{,}424.
The Merkle batch cost stays below \$17 in all cases,
which confirms that the architectural advantage holds
regardless of market conditions.

\subsection{Closed-Form Savings Model}

The gas savings between \Vbase{} and \Vopt{} for a
single verification or revocation call can be decomposed
into two terms.
Let $d$ be the proof depth (equal to the proof array
length):
\begin{equation}
\Delta(d) =
  \underbrace{d \cdot 199}_{\text{T1+T2: per proof step}}
  +\underbrace{144}_{\text{T3+T4: constant}}
\label{eq:model}
\end{equation}

The linear term captures the per-iteration savings from
T1~(unchecked loop increment) and T2~(scratch-space
hashing).
The constant 144 captures T3~(validation splitting,
${\approx}\,96$~gas) and T4~(assembly leaf preimage,
${\approx}\,48$~gas), both applied once per call.
Table~\ref{tab:model} compares the model predictions
with measured gas differences from isolated
\texttt{revokeFromBatch} calls, which use the same
proof-verification path as \texttt{statusWithProof};
Fig.~\ref{fig:model} visualizes the same comparison.

\section{Discussion and Conclusion}
\label{sec:discussion}

\subsection{Engineering Trade-off}

The most important design decision is the architecture.
\Vpacked{} has the cheapest verification but its
issuance cost grows linearly with the number of
diplomas.
Merkle batching reverses this trade-off: issuance is nearly constant
at the batch level, but each verification requires a
proof.
For diploma registries, this trade-off works well---issuance
is a paid operation done by the institution, while
verification is a read-only operation that may occur many times
over the lifetime of the credential.

\subsection{Optimization Hierarchy}

Three levels of optimization can be identified:
\begin{enumerate}
  \item \textbf{Architecture}:
        switching to Merkle batching cuts issuance cost
        by up to 98.9\% per diploma.
  \item \textbf{Code-level tuning}:
        \Vopt{} reduces verification gas by 6.6\% and
        deployment gas by 10.8\% compared to \Vbase{}.
  \item \textbf{Library choice}:
        \Voz{} reduces verification gas by 3.1\%
        compared to \Vbase{}.
\end{enumerate}

Low-level optimizations produce measurable gains but
cannot make up for a costly storage model.
The biggest improvement comes from removing per-record
state writes.

\subsection{Practical Implications}

For small-scale or occasional issuance, per-record
storage is still a good option thanks to its simple
logic and constant-time lookup.
For graduation-scale institutional use, Merkle batching
is the better choice.

OpenZeppelin's \texttt{MerkleProof} is a sensible default
for production---it captures most of the available
savings while keeping the code readable and easy to
audit.
The extra savings from \Vopt{} are worth the added
complexity only when proof verification is on a
performance-critical path.

\subsection{Limitations and Future Work}

This study covers only gas costs on Ethereum~L1 and
does not address privacy, governance, or
interoperability.
All gas measurements use Foundry's local EVM, where
storage slots are warm after the first access within
a transaction.
On mainnet, EIP-2929 cold-access surcharges
(2{,}100~gas per first \texttt{SLOAD}) would raise the
absolute verification cost but would not change the
ranking between variants.
The packed per-record contract is a simplified baseline,
so the comparison should be read as a cost study, not
a feature-for-feature evaluation.

Future work includes running benchmarks on Layer~2
networks, studying calldata-aware designs under
EIP-4844, and testing Verkle-based verification once
it becomes available in production EVM.

\subsection{Conclusion}

This paper compared two deployable architectures for
on-chain diploma verification and derived a closed-form
model that predicts optimization savings across proof
depths.
The main finding is that \emph{architecture matters
more than code-level optimization}: universities that
issue more than a handful of diplomas per cycle should
use Merkle batching, which lowers the per-diploma cost
by two orders of magnitude.
For the verification path, OpenZeppelin's
\texttt{MerkleProof} gives the best balance between
gas savings and code quality; hand-tuned assembly
(\Vopt{}) is only justified under very high throughput
requirements.
As credential storage moves to Layer~2 networks and
EIP-4844 changes calldata pricing, the batching
advantage will only grow---making Merkle-based
registries the natural choice for blockchain-backed
academic credentials.
